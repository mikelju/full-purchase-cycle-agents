# Security findings

Findings left open for the owner's decision.

Since phase 05, SEC-003, SEC-004 and SEC-007 also affect the WhatsApp channel: the message text goes to the model with no delimiting (SEC-003), unmatched texts are echoed in the outbox reply (SEC-004), and the customer is identified from the `from` number only, with no sender verification (SEC-007).

| SEC-022 | Medium | `_receive_one` and `_problem` in `src/purchase_cycle/receipts.py` | The delivered quantity read by the model from a linked delivery note goes straight into `stock.on_hand` and then decides which customer orders are served; code checks only that the SKU is in the catalog and the quantity is a finite whole positive number within a fixed maximum (a non-finite or oversized quantity is parked since commit b5339ef, and a note that would take a SKU stock past that maximum is parked too, with regression tests in `tests/test_receipts.py`), with no check against the purchase order and no human check, and a note linked to a `discrepancies` invoice is received too; a wrong extracted quantity (the document extraction errors DOC-060 and DOC-112 are an example) therefore inflates stock and can serve an order the goods do not cover, and no command reverses a receipt | open - before real stock is managed | phase 10 |
| SEC-023 | Low | `--notes-dir` of `receipts run` in `src/purchase_cycle/receipts_cli.py` and `_insert_note` and `issue` in `src/purchase_cycle/receipts.py` | The folder is taken as given: it is not checked or confined to `data/`, missing parents are created, and the path is stored in `customer_delivery_notes.document_file` as typed (a relative path is stored relative), so `receipts show` later reads whatever path the table holds; the file name is always `CDN-NNNN.txt` from the row id and the text is ASCII only, so customer text never reaches the file name, and a file that already exists is not rewritten, but a file of that name left by someone else is shown as the note | open - accepted for a single local operator | phase 10 |

| SEC-025 | Low | `receipts run` in `src/purchase_cycle/receipts_cli.py` and the receipt graph | Two overlapping `receipts run` processes on one database make the second fail with an `IntegrityError`; the stock stays correct thanks to the `CHECK (on_hand >= 0)` and `UNIQUE` guards, but the second run crashes instead of waiting | open - accepted for a single local operator | phase 10, review round 1 |

## Options

SEC-001:
- Accept the risk and state in the README that all contact data is synthetic.
- Switch the seed to a range that cannot be assigned, or to an obviously fake pattern, and reseed; this changes no labels.
- Also rewrite the dataset sentences, which needs a new dataset version, a rebuilt dataset, new recordings and a new baseline.

SEC-002:
- Keep it, since the git history already carries the author identity.
- Replace it with a GitHub noreply address or remove the email field; the history keeps the earlier value either way.

SEC-021:
- Accept the risk while the data is synthetic.
- Add a retention period and a purge command with the one for SEC-012; `data/` is git-ignored, so the files are not versioned.

SEC-022:
- Accept the risk for the demo and keep receiving only reconciled notes.
- Hold a note for a person to confirm when its quantity exceeds the purchase order quantity or when its invoice has a quantity difference, and add a command that reverses a receipt.

SEC-023:
- Accept the risk for a single local operator.
- Resolve the folder under `data/` and refuse any path outside it, and store the path relative to that folder.

SEC-024:
- Accept the risk while the output is read by a person on a local terminal.
- Print supplier text with `ascii_text` or an escape of control characters, as the customer delivery note file does, and write with an error handler that replaces what the console cannot encode.

SEC-025:
- Accept the risk for a single local operator.
- Take a database lock (a `BEGIN IMMEDIATE` run lock or a lock file) at the start of `receipts run` so the second process waits or exits with one message.
