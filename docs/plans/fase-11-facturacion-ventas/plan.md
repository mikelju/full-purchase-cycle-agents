## Design notes
Written for the owner decisions of 2026-10-16 recorded in the spec: option A for D1 to D4, D6, D7 and D9, option B for D5 and D8.
- New module `purchase_cycle/sales.py`: invoicing, signed note reading and linking, accepted quantities, sales matching, correcting documents, the `sales` graph, and the `run_invoicing`, `run_scan`, `list_sales` and `show_invoice` functions used by the CLI, the evaluations and the demo.
  It imports no `llm` symbol, and a test asserts this.
- New module `purchase_cycle/customer_responses.py`: response facts, drafting call, fact check, template, storage, the `customer_response` graph (`draft`, `review`, `send`, `close`), and `draft_responses`, `approve_response`, `reject_response`, `response_of`.
  It reuses `claims.money_amounts`, `claims.mentions`, `claims.AMOUNT_TOLERANCE` and the `_paused`, `_resume` and `DecisionRefused` pattern by import; no phase 09 code changes.
- New module `purchase_cycle/sales_cli.py` with `add_sales_commands(sub)`, registered from `cli.main` as `receipts_cli` is; `cli.py` only gets the registration line and the `sales-demo` handler.
- Tables in `db.SCHEMA`, all `CREATE TABLE IF NOT EXISTS` (C2): `customer_invoices`, `customer_invoice_lines`, `signed_delivery_notes`, `signed_note_incidents`, `sales_reconciliations`, `sales_discrepancies`, `customer_corrections` (with its lines, kind `credit_note` or `corrective_invoice`), `customer_responses` (with `draft_source` checked in `model`, `template`); `db.TABLES` and `row_counts` stay as they are.
- Folders in `config.py`: `CUSTOMER_INVOICES_DIR`, `SIGNED_NOTES_INBOX` (demo inbox), `CUSTOMER_OUTBOX`, all under `data/`.
- Generalised `classify` (D3, C6): `reconcile_match.classify(order, invoice_lines, note_lines)` accepts `order` with a `lines` list as well as the one-line form; the one-line form is wrapped into a one-item list, so the phase 08 call sites and results stay byte for byte the same.
  The sales call passes order lines at the invoice unit prices, our invoice lines, and the accepted quantities as note lines; an accepted SKU with no invoice line gives a `quantity` row with invoiced 0 (spec, Scope).
- Correcting documents (D4): one credit note from the rows with incident `missing` or `damaged` (negative lines), one corrective invoice from the rows with incident `extra` (positive lines); totals are the sum of their lines rounded to the cent.
- Model task `RESPONSE_DRAFTING` in `llm.py`: name `response_drafting`, tool `record_response_body`, instructions `RESPONSE_DRAFTING_INSTRUCTIONS`, schema `ResponseBody(body: str)` with `extra="forbid"`; `config.RESPONSE_DRAFTING_RECORDINGS_PATH` = `evals/recordings/response_drafting.jsonl`; the demo records into `evals/recordings/sales_demo.jsonl`.
  The prompt holds the facts as one JSON object with sorted keys and amounts with two decimals, so the recording key is stable; no existing task, prompt or recording is touched.
- Fact check `check_response(body, facts) -> list[str]` in `customer_responses.py`, an empty list meaning pass: invoice and delivery note numbers appear; every incident SKU appears with its units in a sentence that names it; every document number appears with its absolute total; every money amount is within half a cent of a fact value (unit prices, line totals, document totals, invoice net total); ASCII and at most `MAX_RESPONSE_BODY = 3000` characters.
  The same function is the grader of `response_drafting`, defined once and imported by the evaluation.
- Template fallback and failures as phase 09: `InvalidModelOutput` or a failing check stores the template with source `template` and parks one `failures` row (channel `sales`, step `response_drafting`, thread `response-SINV-NNNN`, status `needs_review`); `MissingRecording` stops the command.
- Offline path: every test and `npm run check` run with no key; drafting tests use hand-written recordings or a test double of the model client that counts calls, as phase 09; `customer_response` drafts through the test double; `response_drafting` and `sales-demo` replay the recordings stored in Batch G.
  Until Batch G, the demo test writes a temporary recordings file for its prompts, as phase 09 increment 15 did, and `response_drafting` stays out of `ALL_SUITES`.
- Phoenix (D8, C15): change 013 tracing (`PHOENIX_TRACING=true`, `npm run phoenix`, endpoint `127.0.0.1:6006`) is reused unchanged; a replay `sales-demo` with tracing on gives the graph and node spans for free, so the trace shape is checked offline in increment 15 and only the model-call span needs the live run of increment 19.
- Registration in `harness`: `SUITES` and `ALL_SUITES` grow at the end by `sales_reconciliation`, `customer_response`, then `response_drafting` once its baseline exists; it does not join `UPLOAD_SUITES` (LangSmith is left to a later change); earlier tests that pin the suite order change additively, each recorded as a deviation.
- Cost: about 15 calls per development round for up to three rounds, about 45 for the test record and about 3 for the demo record, under 1 USD expected against the 5 USD ceiling (D9).

## Rules for executors
- Execution starts from the approved frozen spec; changing a criterion needs a deviation approved by the owner.
- Each increment is sized for one Sonnet writer with a context ceiling of about 100k tokens; it starts in a fresh session from this file and Git, marks its increment `[x]` with its evidence and commits with a standalone `git commit -m "Phase 11: <increment>"` and no co-author line.
- Failing tests first: each increment adds its tests, runs them to see them fail for the expected reason, then implements.
- Targeted checks during an increment (`uv run pytest -q <files>`); the coordinator runs `npm run check` between batches, and the next batch only starts from a green check.
- Batches A to F run with `ANTHROPIC_API_KEY` and `LANGSMITH_API_KEY` unset (`unset ANTHROPIC_API_KEY LANGSMITH_API_KEY`) and make no model call; only Batch G uses the owner's key.
- The Windows machine can raise subprocess launch errors (exit code 0xC0000142) when several suites or subprocess tests run concurrently; rerun the failing command alone before treating it as a failure, and note the rerun in the evidence.
- Search before reading; read large files by chunks (`cli.py`, `claims.py`, `receipts.py`, `claim_approval_eval.py`, `claim_eval.py` are long); reuse `db.park_failure`, `graph.sqlite_checkpointer`, `sim_clock`, `review.review`, `quotes._write_email`, the `receipts` delivery note writer style, the `claims` drafting and decision functions, the `claim_dataset` and `claim_eval` modules, the `claim_approval_eval` and `goods_receipt_eval` scenario, oracle and gate patterns, `stats.wilson_interval` and `stats.mcnemar_exact`.
- No new dependencies; the 5 USD ceiling of D9 is a limit, not a budget; every live run logs calls, tokens and cost, and the running phase total is written in its increment; no run starts that could pass the ceiling; the agent never reads `.env`, and live runs are run by the owner or with the owner present, with LangSmith tracing off.
- No change to phase 01 to 10 prompts, recordings, datasets, baselines, gates, sample documents or graphs; the only earlier code changes allowed are the generalisation of `classify`, the `cli.main` registration line and the harness registration; every earlier test edit is a deviation.
- Evidence files go to `.evidence/fase-11/`.
