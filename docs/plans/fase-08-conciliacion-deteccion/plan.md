## Design notes
Written for the owner decisions D1 to D11 of 2026-10-13 recorded in the spec.
- New module `purchase_cycle/reconciliation.py`: folder reading, content hash, extraction call and storage, linking, the `reconcile` graph (`build_reconcile_graph` with the nodes `read`, `extract`, `link`, `match`, `store`, no interrupt), the scan, list and show functions, and the demo seeding helper (D1 to D4, D7, D8).
- New module `purchase_cycle/reconcile_match.py`: the pure matching and classification of one invoice against one purchase order and at most one delivery note, with the constants `PRICE_TOLERANCE = 0.01` EUR per unit and `QUANTITY_TOLERANCE = 0` (D5, D6). It imports no model client, so "no model call during matching" holds by construction and a test asserts it (C8).
- New model task `SUPPLIER_DOCUMENT_EXTRACTION` in `llm.py` (name `supplier_document_extraction`, tool `record_supplier_document`) with its instructions, a Pydantic answer schema with `extra="forbid"` and strict types, and the path constant `SUPPLIER_DOCUMENT_RECORDINGS_PATH` in `config.py` pointing to `evals/recordings/document_extraction.jsonl`; the demo uses its own file `evals/recordings/reconcile_demo.jsonl`, as `quotes_demo.jsonl` does. Existing tasks and recordings are not touched (D1, C16).
- Answer schema: `kind` (`invoice` or `delivery_note`), `number`, `po_reference` as written (nullable), `issue_date` (nullable), `currency` (nullable), `supplier_text` (nullable, name or email as written, see ambiguity A1 in the Results notes) and `lines` with `product` as written, `quantity`, `unit_price` and `line_total` (the last two null on a delivery note). Deterministic checks after extraction, in code: kind known, at least one line, quantities positive numbers, currency EUR (D3).
- The prompt holds the text of the document only, read with `email_order.pdf_text` and `email_order.xlsx_text` for `.pdf` and `.xlsx` and plain UTF-8 for `.txt`, cut at a length cap like `MAX_EMAIL_TEXT`; the file name is never in the prompt (D2). The catalog is not in the prompt: SKUs are written in the document or resolved afterwards.
- New tables in `db.SCHEMA` (all `CREATE TABLE IF NOT EXISTS`, so a phase 07 database only gains them): `supplier_documents` (id, kind, number, po_reference, purchase_order_id nullable, supplier_code nullable, issue_date, currency, source_file, content_hash unique, status in `extracted`, `linked`, `unlinked`, `extraction_failed`, reason, created_at from the simulated clock), `document_lines` (document_id, line_no, sku nullable, product_text, quantity, unit_price nullable, line_total nullable; primary key document and line), `reconciliations` (id, invoice_id unique, purchase_order_id, delivery_note_id nullable, result in `matched`, `discrepancies`, `awaiting_delivery_note`, reconciled_at) and `discrepancies` (id, reconciliation_id, sku, type in `price`, `quantity`, `extra_line`, `missing_line`, expected, found, unit_amount, amount; unique on reconciliation, sku and type). `db.TABLES` and `row_counts` stay as they are, so the new tables do not enter the seed row counts (C2).
- Idempotence by content hash: `scan` hashes each file (SHA-256) and skips a hash already stored, so a second scan of the same folder reads no file into the model, adds no row and calls no model (C8). A file whose hash is new but whose invoice or delivery note repeats one already linked to the same order is stored `unlinked` with reason `duplicate` (D4).
- Linking: the reference is normalised with a regular expression for `PO-NNNN`; unknown number, missing reference or supplier mismatch store `unlinked` with reason `no_reference`, `unknown_order`, `supplier_mismatch` or `duplicate`. The supplier is resolved from `supplier_text` against `suppliers.name` and `suppliers.email`; see ambiguity A1 (C4).
- Line resolution: a line is matched by SKU when its product text is a catalog SKU or name via `web_form.match_key` and `web_form.catalog_index` (the phase 02 deterministic catalog matching); text that resolves to nothing becomes an extra line with a null SKU. No model call is added for it (D5).
- Order of arrival: the reconciliation is keyed by the invoice; a delivery note stored before its invoice waits as `linked`; when the invoice is matched, the note of the same order is looked up. A later scan that brings the note updates the same `reconciliations` row (result, `delivery_note_id`, `reconciled_at`) and replaces its `discrepancies` rows in one transaction, never inserting a second reconciliation (C7).
- Matching rule: price difference when `abs(invoice price - order price) > 0.01`, stored per unit and total (`unit_amount` times invoiced quantity); quantity difference when the invoice quantity differs from the ordered quantity or, if a note exists, from the delivered quantity, expected value being the one that differs; extra line for an invoice SKU absent from the order; missing line for an order SKU absent from the invoice; a line can carry price and quantity rows. `matched` only with no row; `awaiting_delivery_note` whenever no note exists yet, as the spec three-way rule states; price and line differences found meanwhile are already stored as `discrepancies` rows, the delivery check is not made, and the note completes the same reconciliation to `matched` or `discrepancies` (C5, C6, C7).
- Reconciliation time and document creation time come from `sim_clock.now`; the reconciliation id printed is `INV-NNNN` from the invoice document id (spec Assumptions).
- Extraction failure parks one `failures` row through `db.park_failure` with channel `reconcile`, thread id `doc-<content hash first 12>`, source the file path, step `document_extraction`; the model node uses `llm.MODEL_RETRY` for transient errors, a schema failure is not retried by the graph and is stored as `extraction_failed`, and the other files go on (C3).
- Graph: one invocation per document with `thread_id` `reconcile-<hash prefix>`, checkpointed with `graph.sqlite_checkpointer`; no `interrupt`. `scan` iterates the folder in sorted order, invokes the graph per new file and, after the folder, runs the matching for every invoice whose inputs changed, so the order of files in the folder does not change the result (C8). One trace per document with one span per node follows from this shape (C15).
- CLI in `cli.py`: `reconcile scan FOLDER`, `reconcile list` and `reconcile show INV-NNNN`, each with `--db`, `--checkpoints` and (scan) `--mode` defaulting to replay with `--recordings`; `reconcile-demo` with `--mode`, `--examples` and `--workdir`, following `quotes-demo`. `show` of an unknown id exits 1 with a message. The module command group is `reconcile`.
- Demo database seeding: `reconcile-demo` does not re-run the quotes module (spec assumption). It clears its work folder (never the data folder), runs `db.seed`, then `reconciliation.seed_demo_orders(conn, path)` inserts, from the versioned `examples/invoices/purchase_orders.json`, one `quote_requests` row with status `ordered` and its one `purchase_orders` row per order, because `purchase_orders.request_id` is a required foreign key. Supplier, SKU, quantity, unit price and expected delivery are listed in that file. Each later step (`scan`, `list`, `show`) runs in its own subprocess on the same files, as `quotes-demo` does.
- Sample documents in `examples/invoices/documents/` in the three formats, written for the seeded orders: a matched invoice with its delivery note, one invoice each for price, quantity (against the order), quantity (invoiced above delivered), extra line and missing line, one invoice with no delivery note, one document with an unknown order and one with a wrong supplier. The first scan reads the folder with the notes of the awaiting invoice held back in a second folder `examples/invoices/later/`, scanned in a second step, to show the completion of the same reconciliation (C7, C14).
- `document_extraction` evaluation: modules `evaluation/document_dataset.py` (seeded planning script, `SEED = 20261013`, ten categories of at least 10 documents, validation, blind export for the clean-context second pass, `.txt` texts plus a rendered share in PDF and Excel, fixed 25% development and 75% test split) and `evaluation/document_eval.py` (runner, graders, Wilson intervals, critical errors, McNemar regression gate, baseline); data in `evals/datasets/document_extraction/` (`plan.jsonl`, `dataset.jsonl`, `second_pass_review.jsonl`, `texts/`), baseline in `evals/baselines/document_extraction.json`. It is modelled on `offer_dataset.py` and `offer_eval.py`, and the PDF and Excel rendering uses `pypdf`-readable PDFs made with the already present libraries only (no new dependency; if rendering a PDF needs one, execution stops and asks the owner).
- `reconciliation_matching` evaluation: module `evaluation/reconcile_eval.py` and at least 40 cases as `evals/datasets/reconciliation_matching/RM-NNN.json` (documents given as already extracted answers by a test double of the model client that fails the test if called during matching), run through the CLI functions on a temporary database; deterministic grader on the database and the printed output, critical errors counted against an oracle apart from the module, as `quote_decision_eval.py` does.
- Registration: `harness.SUITES` and `ALL_SUITES` grow by `document_extraction` then `reconciliation_matching`, in that order, at the end; `document_extraction` joins `UPLOAD_SUITES`, `reconciliation_matching` does not, like `quote_decision` (D9).
- The phase 05 test `tests/test_whatsapp_eval.py` (suite order of `eval all`), `tests/test_offer_eval.py` (position of `offer_extraction`) and the `eval-upload` test in `tests/test_web_form_eval.py` (stub for the new uploadable suite) change additively; each is recorded as a deviation when it happens, as DV-01 and DV-02 of phase 07.
- Cost: about 100 calls for tuning on the development split, about 75 for the test record and a few for the demo, under 1 USD expected against the 5 USD ceiling (D11).

## Rules for executors
- Execution starts from the approved frozen spec; changing a criterion needs a deviation approved by the owner.
- Each batch is sized for one writer agent with about 90k tokens of context; it starts in a fresh session from this file and Git, implements its increments in order, marks each one `[x]` with its evidence and commits before the context runs out.
- Failing tests first: each increment adds its tests, runs them to see them fail for the expected reason, then implements.
- Before closing a batch, `npm run check` passes (pytest quiet) and the batch commit is made; the next batch only starts from a green check.
- Run checks and tests with `ANTHROPIC_API_KEY` and `LANGSMITH_API_KEY` unset (`unset ANTHROPIC_API_KEY LANGSMITH_API_KEY`), except in the live tuning and record step of increment 11 and the live demo record of increment 13, which run with the owner's key present.
- The Windows machine can raise subprocess launch errors (exit code 0xC0000142) when several suites or subprocess tests run concurrently; rerun the failing command alone before treating it as a failure, and note the rerun in the evidence.
- Search before reading; read large files by chunks; reuse `db.park_failure`, `graph.sqlite_checkpointer`, the `llm` record and replay client and `MODEL_RETRY`, `email_order.pdf_text` and `xlsx_text`, `web_form.catalog_index`, `sim_clock`, `stats.wilson_interval`, `stats.mcnemar_exact`, `stats.target_cells` and the phase 05 report and critical-error patterns.
- No new dependencies; the 5 USD ceiling of D11 is a limit, not a budget, and live calls stop before a run that would pass it; the agent never reads `.env`, and live runs that need the owner's key are run by the owner or with the owner present.
- No change to phase 01 to 07 prompts, recordings, datasets, baselines, tables or gates, nor to the quotes sample data, except the named suite-order, `eval-upload` and seed tests, each recorded as a deviation.
- Evidence files go to `.evidence/fase-08/`.
