# Deviation 05.1 - Evaluation fixes from the external audit

Status: approved
Phase: `spec.md` and `plan.md` in this folder (spec approved on 2026-10-09, no increment started)

## What happened
An external portfolio audit dated 2026-10-08 reviewed the repository at commit `b5a9f8b`.
Its phase 05 recovery findings (idempotent store, crash between commit and checkpoint, retries, invalid output) are already covered by C6 to C10.
The findings below are not covered; each one was checked against the code on 2026-10-09 before writing this deviation.

1. Email grader, unknown lines (`src/purchase_cycle/evaluation/email_eval.py`, `grade`): `email_exact_match` and `out_of_catalog_detection` compare only the count of lines with a null SKU, so an unknown line with the wrong quantity or source still passes.
2. Email grader, repeated lines (same function): `line_recall` is `hits[key] > 0` per expected line, so two identical expected lines and one produced line score 2 of 2; the source of a catalog line is not graded either.
   Re-scoring the stored phase 03 test results with a one-to-one grader over (SKU, quantity, source) and (quantity, source) for unknown lines gives the same 184 of 195 exact emails (94.4%): the published exact-email figure holds, the latent false pass does not.
   Only the exact-email figure was re-scored on 2026-10-09; the other re-scored figures (line recall, line precision, out-of-catalog detection) are verified in increment 25, where any drop stops execution for an owner decision (see the addendum).
   The phase 05 spec reuses these graders for `whatsapp_order_extraction`, so the new suite would inherit both defects.
3. Source provenance: the README says an unknown source stops the email before anything is stored; `email_order.py` keeps it as returned, and `tests/test_email_order.py::test_line_source_is_matched_loosely_and_never_stops_the_email` (case `unmatched-kept`) asserts that.
   No line in the stored phase 03 test results has a source outside its email, so enforcing the rule changes no stored figure.
4. Cross-platform bytes: `email_dataset.py` writes XLSX members with `zipfile.ZipInfo(name, date_time=...)`, whose `create_system` is 0 on Windows and 3 elsewhere, so `test_versioned_dataset_is_the_build_of_the_versioned_texts` passes here (323 passed) and fails on Linux, as the audit observed; this blocks a future Linux CI.
5. Evaluation unit: the five suites and the three planned ones grade components (one line, one email, one doubt, one answer given the gold question); none checks the final business state after a full conversation, so a bad real question or a line lost between steps is invisible.
   No suite counts critical errors that an average cannot compensate: a duplicate order, a price not from the catalog, a line dropped without a question, an order stored with an open doubt, a reply confirming an order that does not exist.
6. Targets and gates: `clarification_detection` reports PASS against thresholds set at its measured level after deviation 04.1 (89.1%, 94.3%, 91.3%); the report does not show that the original 95% target is not met.
   Its false question rate of 0 in 48 has a 95% Wilson upper bound of 7.4%, above the 5% gate, and the report does not show the bound.

Not in this deviation, each with its destination:
- LangSmith feedback missing in clarification experiments (`evaluators=[]`) and remote dataset checks by id only: the catch-up change after the trace quota reset (D10).
- Money as integer cents or `Decimal`, a price and terms snapshot per line, coded approvals: the phase 07 and 08 specs.
- Repeated live trials (pass^k), a run manifest, an independent semantic gold for clarifications and more owner audits: a later change, since they add cost.
- CV, LinkedIn and the other repositories: outside this repository.

## Proposal
A in E1 to E5.
E1, E2, E3 and E5 cost no API calls; the evidence so far is that they keep the exact-email figure (184 of 195) and affect no stored line source, and the other re-scored figures are verified in increment 25 under the stop rule of the addendum; they go first, in a new batch before batch A, so the WhatsApp suite is built on fixed graders.
E4 is recorded after increment 16, once the WhatsApp instructions are frozen, and before the demo of increment 17.

Proposed criteria, frozen when approved:

| ID | Observable criterion | How it is checked |
|---|---|---|
| C20 | The email and WhatsApp line graders match expected and produced lines one to one: a produced line counts for at most one expected line; an unknown line passes only with the expected quantity and source; a catalog line passes only with the expected SKU, quantity and source; the phase 03 baseline re-scored with them keeps its stored figures or the change is reported | Grader tests for omission, duplicate, invention, wrong quantity and false source; re-score output saved as evidence |
| C21 | `order_scenarios` holds at least 30 scenarios with at least 8 per channel, 10 with a clarification, 5 with two answers, 3 with an unknown product, 3 with a crash and resume and 3 with a re-delivered message; each is graded by the final database and outbox state; the report shows scenario success with its Wilson interval, the 90% target met or not, and the McNemar regression gate | Pytest tests over the scenario files; stored baseline and replay run report as evidence |
| C22 | Critical errors are counted per scenario in `order_scenarios` and `failure_recovery` (duplicate order, line price not equal to the catalog price at store time, expected line neither stored nor asked about nor escalated, order stored with an open doubt, reply confirming an order that is not stored or naming another number, line with a source outside its message) and any count above 0 fails the evaluation | Pytest tests that inject each critical error and prove a non-zero exit |
| C23 | Every evaluation report shows, per gated metric, the target and whether it is met apart from the gate result, the counting unit of each interval and, for a zero-event rate, its Wilson upper bound | Replay run of `npm run eval` saved as evidence; report tests |

Changed criteria: C1 and C15 count nine evaluations and C1 runs the byte test on Linux (E3); C8 includes the unknown-source case (E2); C11 allows only the grader tests, the `unmatched-kept` test and the report-format tests to change, and a re-scored email baseline (E1, E2, E5).
The spec "Out" line on phase 01 to 04 gates stays: no threshold changes.

## Decision
The owner chose option A in E1 to E5 and approved the deviation via Lavish on 2026-10-09.
The spec gains C20 to C23 and the changed criteria, the plan gains batch A0 (increments 25 to 28) and increment 24 for E4, and the master plan row 05 is unchanged in scope.

## Addendum - review fixes (owner decision 2026-10-09, chat)
A review of commit `64d4203` found inconsistencies between this deviation, the spec and the plan.
The owner approved the fixes in chat on 2026-10-09; no threshold is lowered.
Two of them are owner decisions on frozen criteria:
- C20 and C11: if any stored figure re-scored with the one-to-one grader drops (exact emails, line recall, line precision, out-of-catalog detection), execution stops and the drop goes to the owner as a decision; it is not merely reported.
  This aligns C20 and plan increment 25 with C11 and with "must not drop" in E1, and supersedes "keeps its stored figures or the change is reported" in the proposed C20 above.
- C1 Linux run: the dataset byte tests run in the WSL Ubuntu distribution already installed on the owner's machine, with no new dependency.
  If they cannot run there without installing new software, the Linux part of C1 is reported as blocked and goes to the owner; nothing is installed without asking.
Other fixes, with no change to any criterion:
- Only the exact-email figure (184 of 195) backs the claim that E1 changes no stored figure; the other re-scored figures are verified in increment 25 under the stop rule above.
- Plan increment 6 tests the out-of-message source case (re-ask once, then `needs_review`) for email and WhatsApp, and increment 2 implements and tests the WhatsApp rule that only `message` is a valid source (C8, E2).
- About 0.45 USD of the D9 ceiling is reserved for the increment 24 live record; prompt tuning goes beyond three rounds only if that reserve stays intact (about 1.75 USD planned).
- Increment 14 cites C20 and C23, increment 24 cites C23 and checks in `git log` that the scripted customer answers are committed before the live record.
- Spec wording: unchanged gates for the five existing evaluations, the WhatsApp task extracts the source too, C20 to C23 follow C19 in the criteria table, and the scripted-answer limitation is listed under known limitations.
